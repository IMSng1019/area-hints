# 阶段 5：机械改名与条件注释

> 前置：阶段 4 完成。本阶段只做**词法级改名**，一行逻辑都不许动。

## 目标

把跨版本"只是名字变了"的 API 差异，用条件注释收进 `src/`，并且**保证可验证、可回滚**。
机械改名是 Stonecutter 最擅长的部分，但也是最容易顺手改错逻辑的部分——所以本阶段纪律优先于效率。

## 已知改名模式（先用 grep 出真实数量，再逐类处理）

| 模式 | 旧写法 | 新写法 | 处理方式 |
|---|---|---|---|
| 标识符构造 | `new Identifier(ns, path)` | `Identifier.of(ns, path)` | 一行条件注释 |
| 世界获取 | `player.getWorld()` | 对应新方法名 | 一行条件注释 |
| 文本/组件 | 旧文本构造方法 | 新构造方法 | 一行条件注释 |
| 注册表 | 旧注册表访问 | 新注册表访问 | 一行条件注释 |
| 映射整体切换 | Yarn 类名与包名 | Mojang 类名与包名 | **不许用条件注释**，见下 |

**最后一类是特例**：1.21.11 之后 Yarn 停止维护，26.x 起改用 Mojang Mappings。类名与包名成体系变化时，条件注释会把 `src/` 变成翻译表，**必须**按阶段 4 的方式用 `versions/` 隔离或按分支独立维护，禁止在共享源码里写两套类名。

## 任务

### Task 1：先产出改名清单，不动代码

**Files:**
- Create: `docs/plans/multiversion/14-机械改名清单.md`

**Step 1:** 全仓库 grep 上述模式（以及你实际发现的其它模式），逐条列出：文件、行号、出现次数、属于哪一代际变化。
**Step 2:** 按"改动类型"分组，每组给出预估行数与影响文件数。
**Step 3:** 明确标出**不属于机械改名**的项（签名变化、控制流变化、类型体系变化），把它们交回阶段 4 的方式处理。
**Step 4:** 只出清单。本步骤零代码改动。

### Task 2：按模式分批改，每批必构建

**Step 1:** 一次只处理**一种模式**，例如先全部处理 `new Identifier`。
**Step 2:** 每批改完，对每个已声明版本各构建一次；失败就把该批回滚，不要带着失败继续下一批。
**Step 3:** 条件注释写成紧凑形式，例如：

```java
// ? if < 1.21 {
/*Identifier id = new Identifier(namespace, path);*/// ? } else {
Identifier id = Identifier.of(namespace, path);
// ? }
```

注意条件链里**只有最后一个分支可以不加花括号闭合**，否则 Stonecutter 会报错。
**Step 4:** 同一文件里条件注释超过 3 处，就是信号：该文件应当搬到 `versions/`，停下来汇报。
**Step 5:** 条件注释必须标注简短中文理由（同一行内），例如 `// ? if >= 1.21 // 1.21 起启用新 API` 的等价写法，便于以后批量清理。

### Task 3：收尾核对

**Step 1:** 统计 `src/` 中条件注释的总数，与清单预估对比，数量异常增长就说明有文件该搬未搬。
**Step 2:** 确认没有把"整块实现差异"用条件注释硬凑（对照阶段 2 的契约）。
**Step 3:** 确认注释风格统一，`// ? if` 前后空格一致（Stonecutter 对格式敏感）。

## 验收标准

- 改名清单存在，且每项都有"已完成 / 移交阶段 4 / 不适用"的状态。
- 每一批改动都能在所有已声明版本上构建通过。
- `src/` 里的条件注释**只出现在机械改名与小差异位置**，单文件不超过 3 处。
- 没有出现"两套类名并存"的共享源码文件。
- 汇报里给出：条件注释总数、按文件分布、以及单文件密度最高的前 5 个文件（用于判断是否需要搬到 versions/）。

## 禁止事项

- 不在本阶段改动任何逻辑、控制流、字段顺序、方法语义。
- 不用正则批量替换后不逐文件复查——每批替换必须人工过一遍 diff。
- 不引入新的依赖版本号。
- 不删除任何已有的版本分支代码来"简化"。
