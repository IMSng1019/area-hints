## 一、对原阶段 0 提示词设计缺陷的判断：**成立**

原要求是：「声明 2 个版本目标（1.20.4 与 1.21.1），让**现有代码**同时编译出两个 jar，且**不许改 src/ 任何文件**」。

**结论：该要求自相矛盾，1.21.1 目标不可能编译现有代码。** 证据分三层，全部为实测，不是推测。

### 1.1 源码对 1.20.4 旧 API 的依赖面（grep 全仓库 src/）

| API / 符号 | 命中次数 | 涉及文件数 | 换代情况 |
|---|---|---|---|
| `PacketByteBuf` | 156 | 38 | 1.20.5 起网络层改为 CustomPayload + PacketCodec |
| `ServerPlayNetworking` | 77 | 18 | 同上 |
| `ClientPlayNetworking` | 84 | 19 | 同上 |
| `HudRenderCallback` | 8 | 4 | 1.21 起回调签名变更 |
| `new Identifier(...)` | 66 | 8 | 1.21 起构造器不再公开 |
| `PayloadTypeRegistry` / `CustomPayload` / `PacketCodec` | **0** | 0 | 全仓库没有任何新式网络 API |

最后一行是关键：代码里**完全没有**新式网络的痕迹，说明这不是"顺手改几行"的差距。

### 1.2 具体符号（文件 + 行号）

- `src/main/java/areahint/addhint/AddHintServerNetworking.java:31` —— `ServerPlayNetworking.registerGlobalReceiver(Packets.ADDHINT_AREA_CHANNEL, (server, player, handler, buf, responseSender) -> { ... })`，即已被移除的 `(Identifier, PlayChannelHandler)` 形态
- 同文件 `:135` —— `ServerPlayNetworking.send(player, Packets.ADDHINT_AREA_RESPONSE_CHANNEL, buf)`
- `src/main/java/areahint/network/Packets.java:12` —— `new Identifier(Areashint.MOD_ID, "area_data")`（该文件是 66 个 `new Identifier(...)` 的集中地）
- `src/client/java/areahint/render/CPURender.java:85` —— `HudRenderCallback.EVENT.register(this::onHudRender)`
- 同文件 `:93` —— `private void onHudRender(DrawContext drawContext, float tickDelta)`
- 同形态还有 `GLRender.java:63/71`、`VulkanRender.java:61/69`、`easyadd/EasyAddRecordingHud.java:26`

### 1.3 目标版本上这些 API 确实不存在（javap 实测对照）

用 Loom 已经解析到本地的**官方 fabric-api / Yarn 映射 jar** 直接反编译对比：

**`net.fabricmc.fabric.api.networking.v1.ServerPlayNetworking`**

| | fabric-api 0.97.2+1.20.4 | fabric-api 0.116.0+1.21.1 |
|---|---|---|
| send | `send(ServerPlayerEntity, Identifier, PacketByteBuf)` | 只剩 `send(ServerPlayerEntity, CustomPayload)` |
| 注册 | `registerGlobalReceiver(Identifier, PlayChannelHandler)` | 只剩 `registerGlobalReceiver(PayloadType<T>, PlayPayloadHandler<T>)` |

**`net.fabricmc.fabric.api.client.networking.v1.ClientPlayNetworking`**：同样，1.21.1 上 `send(Identifier, PacketByteBuf)` 与 `registerGlobalReceiver(Identifier, ...)` 均已消失。

**`net.fabricmc.fabric.api.client.rendering.v1.HudRenderCallback`**

- 1.20.4：`void onHudRender(net.minecraft.client.gui.DrawContext, float)`
- 1.21.1：`void onHudRender(net.minecraft.client.gui.DrawContext, net.minecraft.client.render.RenderTickCounter)`
→ `this::onHudRender` 方法引用直接失配，4 个渲染类全部编不过。

**`net.minecraft.util.Identifier`**（Yarn 映射版实测）

- 1.20.4：`public Identifier(String, String)`、`public Identifier(String)`
- 1.21.1：**没有任何 public 构造器**，只有 `public static Identifier of(String, String)` / `of(String)`

→ 光 `Packets.java` 一处就有 66 处 `new Identifier(...)` 会全部失败。

**判断成立。**「现有代码在 1.21.1 上编译通过」等价于已完成网络层 + 渲染层 + Identifier 的整代移植，与阶段 0「不改业务代码」直接冲突。
探针 C 进一步量化了这一点：仅仅跨一个小版本（1.20.4 → 1.20.6），且只编 `src/main`，就已经产生 **61 条编译错误**（见第三节）。

## 五、对阶段 0 提示词的修订建议（可直接替换的措辞）

### 修订 1：把"两版本目标"改成"一个真实目标 + 一个骨架目标"

原句：
> 「只声明 **2 个版本目标**，让现有代码能同时编译出两个 jar。」

替换为：
> 「声明 2 个版本目标：`1.20.4`（**完整**编译共享 `src/`，产物须与改造前基线在类与资源集合上一致）与 `1.21.1`（**空骨架**，把该版本 loom 的 main/client source set 指向 `versions/1.21.1/skeleton/`，不参与共享 `src/` 编译）。
> **不得要求现有代码在 1.21.1 上编译通过** —— 实测 1.21.1 上 `ServerPlayNetworking.send(Player, Identifier, PacketByteBuf)`、`ClientPlayNetworking.send(Identifier, PacketByteBuf)`、`new Identifier(String, String)` 均已不存在，`HudRenderCallback.onHudRender` 第二个参数已由 `float` 变为 `RenderTickCounter`。1.21.1 目标本阶段的唯一作用是验证"多目标编排 + 骨架化"这条工具链。」

### 修订 2：Gradle / Stonecutter 版本那一句是错的，必须改

原句（`01-阶段0-Stonecutter探针.md` Task 1 Step 2）：
> 「同时把 `loom_version` 从 `1.10-SNAPSHOT` 改成正式版号，并把 Loom 版本考虑为 Stonecutter 支持的版本（Stonecutter 需要 Gradle 8.x，8.12.1 可用）」

替换为：
> 「Stonecutter 的 Gradle 下限必须按版本分别确认，**不要笼统写成"需要 Gradle 8.x"**：
> - Stonecutter **0.8.0 及以上硬性要求 Gradle ≥ 9.0**，在 Gradle 8.12.1 上会直接报 `Stonecutter requires at least Gradle 9` 并中止配置；
> - 本仓库 Wrapper 为 8.12.1，因此若要留在 Gradle 8.12.1，**只能选 Stonecutter ≤ 0.7.11**（本次实测 0.7.11 可用）；
> - 若要使用 0.9.x，必须先把 Wrapper 升到 Gradle 9.x。实测 Loom 1.10-SNAPSHOT + `splitEnvironmentSourceSets()` 在 Gradle 9.5.1 上可正常完成两节点 compile + remapJar。
> 本阶段默认路线：**保持 Wrapper 8.12.1 + Stonecutter 0.7.11**，把"升 Gradle 9 + Stonecutter 0.9.x"列为独立的待决项。」

### 修订 3：删掉"用于覆盖的版本目录"这个隐含前提

原句（`00-总纲与约定.md` 一、总体形态）：
> 「`versions/1.21.1/  ← 放该代际的网络/渲染实现`」

替换为：
> 「`versions/<版本>/ ← 该版本专属实现`。
> **注意：Stonecutter 不会让版本目录里的同名文件覆盖共享 `src/` 里的同名文件**，两者会同时进入 javac 并报 `错误: 类重复`（实测）。
> 因此该代际实现只能走以下三条路之一，必须在阶段 1 定稿：
> (a) 共享 `src/` 只留接口/抽象，版本目录放不同 FQN 的实现类；
> (b) 对该版本显式 `setSrcDirs`／exclude 掉共享 `src/` 中的对应文件（本次骨架化用的就是这一招，已验证可行）；
> (c) 用 Stonecutter 的 `//? if` 条件注释或 `replacements` 在原文件内分支。」

### 修订 4：把探针 C 的目标版本从"期望编过"改成"测量断点"

原句：
> 「追加第三个目标 `1.20.6` … 让 1.20.6 也编译完整的模组代码，看是否仅靠"不改代码或仅允许 ≤3 行改动"就能编过。」

替换为：
> 「追加第三个目标 `1.20.6`，让 1.20.6 编译完整模组代码，**预期结果是失败**，目的是量化 1.20.4 → 1.20.6 的断点规模。
> 已知结论（本次实测）：仅 `src/main` 就 61 条错误，全部集中在 `ServerPlayNetworking.send`（33）、`ServerPlayNetworking.registerGlobalReceiver`（27）、`ServerWorld.getDimensionKey()`（1）。客户端 `ClientPlayNetworking` 一族因 `compileClientJava` 依赖 `compileJava` 而无法单独统计，实际总量更大。
> **1.20.6 不能作为"第二个真实编译目标"**，它和 1.21.1 一样属于需要先做网络层移植的版本。建议第二个真实目标改选 **1.20.1 或 1.20.2**（同代际、Yarn、Java 17、网络 API 同形态），这样阶段 0 才能真正验证"同代际多目标"。」

### 修订 5：明确"原有单版本构建方式"的验收口径

原句：
> 「原有单版本构建方式（普通 `build` 或 `remapJar`）没有被破坏。」

替换为：
> 「原有单版本构建方式等效可用，但**产物路径会变化**：根项目在 Stonecutter 下是 tree，不执行任何构建任务；`gradlew build` 会构建**全部版本节点**，1.20.4 的产物从 `build/libs/` 移到 `versions/1.20.4/build/libs/`。
> 验收口径改为：`.\gradlew.bat :1.20.4:build` 退出码 0，且 `versions/1.20.4/build/libs/areas-hint-fabric-1.20.4-4.6.0.jar` 的 `jar tf` 与基线逐条一致。」

## 六、最终结论

### 1. Stonecutter 能否与 `splitEnvironmentSourceSets()` + 本仓库 Loom 共存？—— **有条件地能**

**能的部分（已实测通过）**

- Stonecutter 0.7.11 + Gradle 8.12.1 + Loom 1.10-SNAPSHOT + `splitEnvironmentSourceSets()`：两目标各自产出 jar，main/client 两个 source set 都正常参与编译，1.20.4 产物与基线在类与资源集合上**零差异**。
- 每个版本一份 `deps.<mcVersion>.<name>` 参数、每个版本独立 java release（17 / 21）均生效。
- 版本变体机制（同 FQN 取不同实现并进入各自产物）工作正常。
- Gradle 9.5.1 上 Loom 1.10-SNAPSHOT 也能跑通（为将来升 Gradle 留了路）。

**条件（三个前提，缺一不可）**

1. **Stonecutter 版本与 Gradle 版本必须配对**：留在 Gradle 8.12.1 就只能用 ≤ 0.7.11；要用 0.9.x 必须升 Wrapper 到 Gradle 9.x。原提示词写的"0.9.7 + Gradle 8.12.1"组合**不成立**。两条路本次**都已实测跑通**（见第四节 B1）。
2. **不能指望版本目录同名覆盖共享源码**，物理隔离方案需按修订 3 重新定稿。
3. **接受产物路径迁移**到 `versions/<v>/build/libs/`，根 `build/libs/` 不再是产物目录。

### 2. 对方案本身的判断

- 阶段 0 的真正否决点（"Stonecutter 能否与 `splitEnvironmentSourceSets()` 共存"）**没有被否决**，工具链这条路是通的。
- 但"两个目标都编现有代码"这个设定是错的，**必须改成"一个真实目标 + 一个骨架目标"**，且第二个真实目标应选同代际的 1.20.1/1.20.2 而不是 1.20.6。
- 阶段 1 的第一件事应该是**网络层抽象（NetworkCompat）**，而不是继续扩版本矩阵：在 1.20.4 → 1.20.6 这**一个小版本**上就有 61+ 条网络层错误，说明网络层是唯一的真断点，且它一解决，1.20.5/1.20.6 这一代际就能整体打开。

### 3. 下一步建议（按优先级）

1. **拍板 Gradle 路线**：留在 8.12.1 + Stonecutter 0.7.11（改动最小、本次已验证），还是升 Gradle 9.x 换 0.9.x（功能更全、Groovy 支持更好，但 Wrapper 是全局改动）。**这是未决项 U1**。
2. 阶段 1 先做 NetworkCompat（`ServerPlayNetworking` / `ClientPlayNetworking` / `PacketByteBuf` 的形状抽象），用 1.20.6 目标当"红灯变绿灯"的量尺。
3. 重写 `00-总纲` 的 `versions/` 物理隔离那一节（修订 3）。
4. 1.21.1 目标在阶段 0/1 保持骨架，等渲染层（`HudRenderCallback` → 新回调、`WorldRenderer` mixin）方案定稿后再打开。

### 4. 未决项（需要你拍板）

| 编号 | 事项 | 备选 | 本次默认选择 |
|---|---|---|---|
| U1 | Gradle 与 Stonecutter 版本配对 | (a) Wrapper 8.12.1 + Stonecutter 0.7.11；(b) Wrapper 升 9.x + Stonecutter 0.9.7 | 已按 (a) 落地并验证；**(b) 也已实测可行**，两条路都通，纯粹看你要不要动 Wrapper |
| U2 | 是否保留 1.20.6 作为常驻目标 | (a) 移出活跃列表（默认 `gradlew build` 保持绿色）；(b) 留在列表里当常驻红灯量尺 | 已按 (a) 落地，`deps.1.20.6.*` 与复现注释都保留 |
| U3 | 第二个"真实编译目标"换成哪个版本 | 1.20.1 / 1.20.2 / 暂不设 | 未动，`settings.gradle` 仍是 2 个目标 |
