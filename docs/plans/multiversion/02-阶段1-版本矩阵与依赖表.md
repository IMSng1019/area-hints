# 阶段 1：版本矩阵、第三方依赖按版本解析与产物元数据

> 前置：阶段 0 收尾（D4 升级）完成。**本阶段不改业务代码**，只产出「能构建的事实」、一份矩阵，以及**按版本解析的第三方依赖**。
>
> **本阶段不新增编译目标**：1.20.6 / 1.21.1 等必须先做阶段 3 的 NetworkCompat 才谈得上真正编译（实测 1.20.6 有 61 条网络层错误）。
> 已定稿决策见 `00-总纲与约定.md` 第 3.5 节（D2 第三方依赖按版本解析、D3 不探 1.20.2、D6 先做网络层）。

## 目标

把我要求的版本清单落成三档（必出包 / 仅声明 / 实验性），逐个确认**官方依赖与第三方依赖是否真实存在**，并把每个版本必需的构建参数写成配置文件。

## 版本清单（已定稿）

`1.20.1 / 1.20.4 / 1.20.6 / 1.21.1 / 1.21.4 / 1.21.5 / 1.21.8 / 1.21.11 / 26.1 / 26.2`

- **1.20.4 为常驻基线**（D1），任何改动后必须与其基线 `jar tf`（456 条）逐条一致。
- **1.20.2 已排除**（D3），不要再加回来。
- 1.20.1 已实测可编译（`src/main` 0 错误、16 处客户端 UI 差异），但**常驻与否由阶段 4 决定**，本阶段只做依赖与元数据准备。

## 任务

### Task 1：逐版本确认可用性（含第三方坐标）

**Files:**
- Create: `docs/plans/multiversion/11-版本矩阵.md`

**Step 1:** 对清单中每个版本，确认三件事并做成一列一列的表：**Yarn 映射是否存在**、**Fabric Loader/Loom 能否解析该版本**、**Java 工具链版本**。
**Step 2:** 对清单中每个版本，逐个确认第三方依赖是否有对应坐标：`Xaero 小地图`、`Xaero 世界地图`、`BlueMap API`、`ModMenu`、`VulkanMod`、`LuckPerms`。**查不到就明确写"该版本无可用坐标"，不要猜、不要留空、不要用相近版本顶替。**
**Step 3:** 按结果分三档：
- **必出包**：官方依赖齐 + 主要第三方依赖齐 + 玩家基数大
- **仅声明**：能编译，但部分第三方功能缺失（必须在表里写明缺哪些）
- **实验性**：能编译但无第三方支持，产物标注"实验性"
**Step 4:** 在矩阵末尾给出结论：三档各是哪几个版本，以及**每个档位需要几套 Java 工具链**。

### Task 1.5（**本阶段的重头戏，优先级最高**）：第三方依赖按版本解析（D2）

**Files:**
- Modify: `gradle.properties`
- Modify: `build.gradle`

**背景（实测）**：当前 1.20.1 节点编的是 **1.20.4 的第三方 jar**——`build.gradle` 只读扁平键 `modmenu_version` / `xaero_*_version`。ModMenu 9.2.0 的 `fabric.mod.json` 声明 `minecraft >=1.20.3`，于是**编译能过、运行时会加载失败**。

**Step 1:** 为每个已声明版本补齐这些键（示例，实际值以查证结果为准）：

```
deps.1.20.1.modmenu=7.2.2
deps.1.20.1.xaero_minimap=<查证：_Fabric_1.20>
deps.1.20.1.xaero_world_map=<查证：_Fabric_1.20>
deps.1.20.4.modmenu=9.2.0
deps.1.20.4.xaero_minimap=25.2.0_Fabric_1.20.4
deps.1.20.4.xaero_world_map=1.39.2_Fabric_1.20.4
```

注意 Xaero 的坐标格式是 `<mod版本>_Fabric_<MC版本>`，**MC 版本段必须与目标版本一致**，不能沿用 1.20.4 的。

**Step 2:** 在 `build.gradle` 里把 `modmenu_version` 等扁平键的读取改为优先读 `deps.${mcVersion}.<name>`、缺失时回退扁平键（与现有 `versionedProp` 一致），**旧键保留不删**。
**Step 3:** 查不到对应版本坐标的第三方依赖：**不要伪造、不要用相近版本顶替**。在**该版本**下移除该依赖，并在 `11-版本矩阵.md` 写明「该版本无可用坐标」，然后汇报。
**Step 4:** BlueMap（`compileOnly de.bluecolored.bluemap:BlueMapAPI`）与 LuckPerms（`compileOnly net.luckperms:api`）同样按版本解析；它们是编译期依赖，同样不能跨版本沿用。
**Step 5:** 改完后跑 `& .\gradlew.bat build --console=plain`，确认 1.20.4 产物与基线 `jar tf` 仍然逐条一致（456 条）。

### Task 2：给每个版本写构建参数

**Files:**
- Modify: `stonecutter.gradle`
- Modify: `gradle.properties`

**Step 1:** 在 `stonecutter.gradle` 声明最终版本列表（只在**必出包 + 仅声明**范围里声明；实验性单独一组，方便一键排除）。
**Step 2:** 为每个版本补齐 `minecraft`、`yarn` 或 Mojang 映射、`loader`、`fabric`、`java` 五项参数。
**Step 3:** 对 26.x 这类改用 Mojang Mappings 的版本，**不要**试图复用 Yarn 的构建脚本，按阶段 0 已验证的方式给它们单独 `buildscript`。
**Step 4:** 缺失的第三方依赖，用版本条件控制依赖声明（只允许出现在**构建脚本**里，不允许出现在 Java 源码里）。

### Task 3：产物元数据按版本区分

**Files:**
- Modify: `src/main/resources/fabric.mod.json`
- Modify: `build.gradle`

**Step 1:** `fabric.mod.json` 的 `depends.minecraft` 改成按版本解析（用资源文件的条件注释或构建脚本替换），**必须保证 1.20.4 产物里仍然是 `~1.20.4`**，不许出现无条件放宽。
**Step 2:** `version` 与产物文件名必须能区分 MC 版本，例如 `areas-hint-4.6.0+1.20.4.jar`；`archives_base_name` 保持 `areas-hint` 不变。
**Step 3:** `suggests` 里 Xaero 的精确版本号要按版本解析；查不到对应版本的，从该版本的产物里移除该条目，不要留错版本号。

## 验收标准

- 矩阵表里**每个版本、每个依赖项都有明确结论**（有坐标 / 无坐标），不允许「待确认」。
- **D2 落地**：每个已声明版本的 ModMenu / Xaero / BlueMap / LuckPerms 坐标都在 `gradle.properties` 里按 `deps.<版本>.*` 显式给出，且 `build.gradle` 按当前节点版本读取；1.20.4 产物与基线 `jar tf` 仍逐条一致。
- 缺坐标的依赖在**对应版本**里被移除（不是全局移除），且矩阵中写明缺失原因。
- 三档划分给出明确理由（依赖齐不齐、玩家基数）。
- 声明的每个版本都能至少构建到"编译通过"程度；不能编译的版本不要留在 `versions()` 里。
- 仍未修改 `src/` 下的业务 Java 代码。
- 汇报里给出：最终 `versions()` 列表、Java 工具链套数、以及第三方依赖缺失清单。

## 禁止事项

- 不因为某版本缺依赖就悄悄把它从清单里删掉——先汇报，由我决定降档还是放弃。
- 不正版化或伪造依赖版本号；查不到就是查不到。
- 不修改业务代码；网络层、渲染层的改动属于阶段 3、4。

## 八、实测修正（2026-10-03，阶段 1 执行时记录）

> 以下三处原文与实测不符，**执行时以实测为准**。证据见 `11-版本矩阵.md` 第六节与 `research/` 下四份调研报告。

| 位置 | 原文 | 实测事实 |
|---|---|---|
| 本文 L27（世代断点表） | 26.1–26.2「Java 21+、Mojang Mappings」 | Java 是 **25**；26.x **完全不再混淆、不需要任何映射**（不是"改用 Mojang 映射"），Loom 侧要换成 no-remap 插件 `net.fabricmc.fabric-loom` |
| 本文 L63（Task 1.5 Step 1 注意） | Xaero 坐标「MC 版本段必须与目标版本一致」 | Xaero 已换命名规则。旧格式段是 `1.20`/`1.21`（不等于目标版本）；判据只能是 Modrinth 的 `game_versions` |
| 本文 Task 1.5 Step 4 | BlueMap / LuckPerms「同样不能跨版本沿用」 | 二者都**不随 MC 版本变化**（jar 内 0 处 `net/minecraft` 引用）。真正要按版本对齐的是**坐标改名带来的字节码版本差异**：旧坐标 `de.bluecolored.bluemap:BlueMapAPI` 冻结在 2.7.2（JVM16），新坐标 `de.bluecolored:bluemap-api` 2.7.3–2.7.8 是 JVM21、2.8.0+ 是 JVM25 |

另有一处措辞需要更正：Task 2 Step 1 说「在 `stonecutter.gradle` 声明最终版本列表」，但按阶段 0 的实测结论，`stonecutter.gradle` 是插件自动生成的文件、**不许手写**，版本列表实际声明在 `settings.gradle` 的 `stonecutter { create(...) { versions ... } }` 里。
