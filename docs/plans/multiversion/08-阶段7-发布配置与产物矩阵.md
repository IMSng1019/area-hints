# 阶段 7：发布配置与产物矩阵

> 前置：阶段 6 完成，所有版本可构建。

## 目标

一次性构建全部已声明版本，产物命名与元数据能明确区分版本，并给出每个版本的"冒烟清单"（功能验证由我手动进游戏完成）。

## 任务

### Task 1：一键多版本构建

**Files:**
- Modify: `stonecutter.gradle`
- Modify: `build.gradle`

**Step 1:** 确认 Stonecutter 的聚合构建任务能一次性产出所有已声明版本的 jar；任务名与用法写进文档。
**Step 2:** 实验性档位的版本单独一组，可一键排除，不阻塞正式产物构建。
**Step 3:** 构建并行度与内存参数保持仓库现状（`org.gradle.parallel=true`、`-Xmx1G`），若多版本下内存不足，先汇报再调整，不要擅自大幅提高。

### Task 2：产物命名与元数据

**Step 1:** 产物名必须包含 MC 版本，例如 `areas-hint-4.6.0+1.20.4.jar`；`archives_base_name` 保持 `areas-hint`。
**Step 2:** 每个产物的 `fabric.mod.json` 里 `depends.minecraft`、`suggests` 必须与目标版本一致；**逐个解包检查**，不许只看构建脚本。
**Step 3:** 确认 1.20.4 产物与改造前产物的资源集合一致（语言文件、mixin 配置、图标齐全）。
**Step 4:** `sourcesJar` 与 `publishing` 配置保持可用，不要因为多版本而失效。

### Task 3：冒烟清单与说明

**Files:**
- Create: `docs/plans/multiversion/15-发布与冒烟清单.md`
- Modify: `README.md`

**Step 1:** 清单按版本分组，每版本列出需要人工验证的项：区域数据同步、进入区域提示、`/areahint reload`、EasyAdd 记录顶点、维度域名、渲染模式切换、Xaero/BlueMap 能力（若该版本支持）。
**Step 2:** 明确写清"哪些版本是必出包、哪些是仅声明、哪些是实验性"，以及每个档位的功能差异。
**Step 3:** README 增加一段使用说明：哪个 jar 对应哪个 MC 版本、需要什么 Java 版本、哪些第三方 mod 是可选增强。
**Step 4:** 不要写"支持全部版本"这类无法兑现的表述，按矩阵如实描述。

### Task 4：CI 检查（只做构建，不做发布）

**Step 1:** 若仓库有 GitHub Actions 工作流，确认多版本构建能跑通；**不新增任何发布、上传、部署步骤**。
**Step 2:** 工作流里不引入需要网络凭据的步骤。

## 验收标准

- 一条命令能产出全部正式档位产物；产物名可区分版本。
- 逐个解包核对了 `fabric.mod.json` 的版本相关字段。
- 冒烟清单存在且分工明确（构建由我验证、功能由我手动测）。
- README 描述与实际支持矩阵一致。
- 未执行任何发布动作、未提交任何东西。

## 禁止事项

- 不执行 `publish`、不上传任何平台、不创建 tag、不提交。
- 不修改已发布的旧产物。
- 不在构建脚本里硬编码本地绝对路径。
