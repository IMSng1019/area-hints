# editviz 填充与边界笔的浮点伪洞修复

## 问题与现场

用户在新建域名时看到“边界包含洞，请填满洞后再保存”，同时无法简化边界。通过 Computer Use 查看 Minecraft 1.20.1 中的“须弥”草稿，确认存在该报错，完整选区在当前缩放下没有明显孔洞。观察只涉及窗口和视图，没有修改或提交草稿；截图无法证明是否存在极小内部轮廓。

代码侧独立复现了两个会产生相同症状的浮点问题，均可在 Java 17、21、25 重现：

1. 选区笔填洞：原三角形为 `(0.8, 0.2)、(10.3, 3.1)、(5, 10)`，用一格宽笔画经过 `(5, 5)、(5, 0)、(3, 0)`。填洞前存在新闭合区域，旧填充实现反复对同一小数斜边做差集、并集后，留下约 `9.86e-32` 平方格的三角形伪洞。
2. 边界笔：原三角形为 `(17.7, 0)、(-2.8, 4.9)、(-9.6, -16.6)`，不设地形、父域名或同级限制，笔宽为 8，依次经过 `(-7, 4)、(24, -13)`。旧实现先减去旧域名、裁剪、再并回，留下约 `4.55e-16` 平方格的伪洞；对空禁区的减法也会触发斜边重新正规化。

保存检查发现正面积内环即报包含洞；交互简化遇到多个轮廓则直接返回原稿。因此，极小伪洞会同时阻止保存与简化。

## 修复范围

- `VizEditGeometry.fillNewlyEnclosed` 直接用外环重建填充后的选区，将旧洞与当前洞的交集反向写回同一路径，避免再次将新洞与原斜边做并集。先正规化外环，确保嵌套岛内的旧洞正确保留。
- `BoundaryBrush` 保留完整填充选区，同时按原来的新增面积裁剪和旧面积并回顺序生成结果。只有硬禁区和自然禁区均为空、原结果出现正面积内环、完整选区为合法单环且没有损失旧面积时，才采用完整选区，绕开本次拆分、重组造成的伪洞；原本合法的结果和有约束的裁剪顺序保持不变。差集里的纯往返线只通过重复点、精确共线清理识别为退化路径，不用面积容差。
- 根目录和 `modern` 两套实现与测试同步；没有引入 Minecraft API、JSON 格式或翻译变化。
- 不按面积阈值忽略孔洞。真实的旧洞、用户擦除的洞、父域名、同级域名和自然岸线限制继续保留。

## 验证与限制

- 新增回归在旧实现中先准确失败于 `geometry_holes`，修复后通过，并验证保存和简化入口。
- 独立运行 `VizEditGeometryTest`：Java 17、21、25 各 31/31 通过；modern 源码在 Java 25 中 31/31 通过。
- 最终 `BoundaryBrushTest` 在实际 Java 17、21、25 中各 30/30 通过，覆盖无禁区斜边伪洞、父域名外的已有小数边界在内部涂画后精确保留，以及既有父域名、同级域名和自然岸线限制。
- 两组各 30000 个输入的临时差分探针覆盖随机小数斜边笔画、整数多洞加笔与嵌套岛。
- 独立审查对最终边界笔做 10000 组受约束小数选区对照：没有新增旧面积损失，没有旧合法结果变成非法，13 组结果改善。
- 最终执行 `.\gradlew.bat --gradle-user-home .gradle-home '-Dorg.gradle.java.home=J:/mc/jdk25' build --offline --no-parallel --no-daemon --console=plain`，12 个活跃版本全部编译、测试、打包成功，耗时 1 分 43 秒。此前沙箱内构建被 Loom 系统临时文件访问权限阻止，最终使用已获准的沙箱外离线构建。
- 按 `settings.gradle` 的活跃节点汇总 JUnit XML：2198 项测试，零失败、错误或跳过；旧版与 modern 四个对应源码／测试文件内容一致，`git diff --check` 通过。
- 此修改防止上述复现路径生成新的伪洞，不宣称消除所有 Java2D 布尔运算的浮点误差。有约束的边界笔继续使用原来的裁剪路径。已经留在正在运行的旧版游戏草稿里的孔洞不会自动消失，也没有对用户现场草稿执行覆盖、保存或重新加载。
