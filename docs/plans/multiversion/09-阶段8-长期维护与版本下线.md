# 阶段 8：长期维护与版本下线

> 前置：阶段 7 完成，多版本产物已能稳定构建。

## 目标

把"以后新增一个 MC 版本"和"下线一个老版本"变成可复制的标准动作，避免每次都要重新判断该放哪、该改什么。

## 任务

### Task 1：新增版本的标准步骤

**Files:**
- Create: `docs/plans/multiversion/16-新增版本操作手册.md`

**Step 1:** 写成编号步骤，至少覆盖：确认 Yarn/Mojang 映射与 Java 工具链 → 确认第三方依赖坐标 → 在 `stonecutter.gradle` 声明版本 → 建 `versions/<版本>/` → 判定是否落在已有代际（落在则目录留空）→ 构建 → 按需补条件注释或 `versions/` 实现 → 解包核对 `fabric.mod.json` → 加入冒烟清单。
**Step 2:** 给一个"判断该不该新建实现文件"的决策树：先看该版本落在哪个已知世代 → 同世代一律复用 → 只有跨世代才写新实现。
**Step 3:** 附上已知世代表（网络代际、渲染代际、映射代际），以后新版本先查这张表。

### Task 2：版本下线策略

**Step 1:** 定义三档状态：**维护中**（接受功能与修复）、**仅修复**（只接严重问题）、**已归档**（不再构建）。
**Step 2:** 定义降档触发条件（例如上游依赖不再提供坐标、映射不再更新、连续若干版本无玩家反馈）。
**Step 3:** 定义下线动作：从 `versions()` 移除、对应 `versions/<版本>/` 目录处理方式、README 与矩阵同步更新。
**Step 4:** 明确"归档不等于删除代码"——历史实现文件保留在 main 上，移除的只是构建声明。

### Task 3：映射切换的长期预案

**Step 1:** 针对 Yarn → Mojang Mappings 的切换，整理一份**当前仓库实际用到的**名字对照表（只列本模组真正用到的类与方法，不要抄整张映射表）。
**Step 2:** 明确规则：**映射不同代的版本不共用同一份 `src/` 类名体系**，必须以独立节点（独立 buildscript / 独立分支形态）维护，禁止在共享源码里写两套类名。
**Step 3:** 给出迁移顺序建议（先切构建脚本与依赖，再逐个文件改类名，每批构建验证）。

### Task 4：定期体检

**Step 1:** 定义一份可周期执行的检查项：`src/` 条件注释密度、`versions/` 空目录数量、每版本依赖可用性、产物元数据正确性、语言文件键集合一致性。
**Step 2:** 检查项要能给出**数字**（例如条件注释总数、越界 import 数），便于判断是否在退化。
**Step 3:** 把检查项整理成一段可直接复制执行的命令清单（grep 命令即可，不要写测试代码）。

## 验收标准

- 操作手册能让"新增一个版本"在不重新做架构判断的情况下完成。
- 三档状态与降档、下线动作定义清晰，且与阶段 1 的矩阵、阶段 7 的 README 表述一致。
- 映射对照表只包含本仓库实际使用的名字。
- 体检清单每项都能产出数字。

## 禁止事项

- 不写测试代码、不写 CI 发布流程。
- 不删除历史版本的实现文件。
- 不引入新的构建插件或架构层。
