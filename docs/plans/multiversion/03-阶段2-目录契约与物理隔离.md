## 契约（须落成文档并逐条执行）

### 规则 1：`src/` 是共享内核

`src/` 下的文件**不允许 import `net.minecraft.*`**（渲染可视化控制器这类纯业务编排除外，见规则 4）。
判定方法：一个文件如果没有 Minecraft API 依赖，它就不该有任何版本分支。

现状参考：`PolygonGeometry`、`RayCasting`、`JsonHelper`、`AreaData`、`ColorUtil`、`FileManager` 这类应当完全无版本概念。

### 规则 2：`versions/` 只放「不同 FQN 的实现」

某个能力在各版本间**整块实现不同**时，`src/` 只保留**接口**，实现在 `versions/<该代际最低版本>/` 下写**一份**，同代际其它版本目录留空。

**硬约束（实测）**：版本目录里的类**不得**与共享 `src/` 中任何类同名同路径——同名即 `错误: 类重复`。
类名建议带版本后缀便于辨认，例如 `Identifiers1204` / `Identifiers1211`。

### 规则 3：条件注释只用于小差异

单文件、单方法内、**≤3 行**的差异才允许用 `//? if`；超过就是信号：应该拆到 `versions/`。

### 规则 4：业务编排不进 `versions/`

`*VisualController`、`*Manager`、`*UI` 这类只做业务编排的文件保持在 `src/`，版本差异通过调用接口消化。

### 规则 5：共享侧怎么挑实现（交接点）

实现类名在其它版本里不存在，因此共享侧不能写死。三种接法按优先级：

1. **每个版本目录各放一个同名工厂类**（推荐；每个节点只挂载一个版本目录，不会冲突）；
2. 入口处集中写 2–3 行条件注释（入口只有一个时可接受）；
3. 反射用字符串类名（**不推荐**，丢失编译期检查）。
