# Fabric 后续版本适配计划

> 执行方式：主代理与子代理在 main 上按文件分工；用户已授权自主规划、实施与逐版本提交，无需 worktree。

**Goal:** 从已支持的 1.21.5 继续适配至官方最新稳定版，每个版本保留可追踪的构建、测试与提交记录。

**Architecture:** 延续 Stonecutter 共享源码与 versions 下版本专属平台实现，优先隔离渲染、GUI、网络和第三方 API 差异。26.x 的官方命名与 no-remap 构建单独处理，已有版本持续参与回归。

**Tech Stack:** Java 17/21/25、Fabric、Gradle、Stonecutter、JUnit 5。

## 执行顺序

1. 查询 Mojang manifest、Fabric 元数据和第三方发布信息，核实最新版；先完成已有依赖配置的 1.21.8，再推进 1.21.11、26.x 稳定发布节点。
2. 每个节点先启用构建并复现编译错误，读取对应游戏/API 的实际签名，按独立文件分派修复；保留原有域名行为与翻译。
3. 对逻辑变化补充有意义的回归测试；API 迁移通过目标编译、现有 JUnit、协议/通道校验、产物与 mixin 检查验证。
4. 运行目标 `:<version>:build` 与已支持版本回归，审查 diff，记录未进行的游戏内验证，提交 `Add Fabric <version> support`。
5. 每完成一版更新本文件的交接状态，然后继续下一版。当前工具没有手动清空/压缩上下文接口；使用此记录衔接自动压缩，避免丢失任务。

## 26.x 构建与源码设计

用户已授权自主选择方案并持续实施。采用 Stonecutter 的 `modern` 分支（官方文档确认每个 branch 有自己的共享 `src` 与 `versions`），同一构建内对该分支使用 no-remap Loom 1.17.21；旧分支继续 remap，同一根属性表统一依赖。

- 相比全仓改为官方命名，此方案保留旧版已经验证的共享源码；相比额外独立构建，此方案继续使用现有 Gradle 入口与任务聚合。
- 完成 1.21.11 后，将其预处理共享源码与版本实现合并到 `.deps` 临时输入，使用 Loom/Mercury 与 MixinRemapper 转为同版官方命名，按清单恢复 main/client 分离；所有业务、集成、资源和测试必须保留。
- 从官方命名的 1.21.11 作为锚点迁移至 26.1.2，使用 Java 25 工具链，随后逐节点适配 26.2 和 26.3。节点专属图形/第三方实现仍放版本目录。
- 资源继续复用根资源目录，不复制或损坏 11 种翻译；成品路径纳入 CI 上传。运行完整单元测试、入口和 Mixin 检查、类与协议完整性检查后逐版本提交。
- 如果同构建实际出现无法隔离的插件配置问题，再用 included build 隔离；不得以空壳、注释整个功能或跳过客户端编译视为适配完成。
- 当前进度：1.21.10 已提交 `9b6b956`；1.21.11 已通过九节点完整构建，提交后进入正式 26.x 源码迁移。
