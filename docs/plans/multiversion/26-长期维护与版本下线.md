## 一、版本生命周期：三档状态

### 1.1 状态定义

| 状态 | 含义 | 接受什么 | 构建义务 | 产物 |
|---|---|---|---|---|
| **维护中** | 正常支持 | 新功能 + 修复 | 每次改动后都必须编译绿 + 三件套 PASS | 正常出（属于"必出包"） |
| **仅修复** | 冻结功能 | 只接严重问题（崩溃、数据损坏、协议不兼容） | 只在发该版本修复包时构建 | 只在修复时出 |
| **已归档** | 不再支持 | 不接 | 无 | 不再产出（历史产物保留） |

### 1.2 状态 ≠ 发布档位（两者正交，别混）

- **发布档位**（必出包 / 仅声明 / 实验性）回答"投不投入适配"。
- **生命周期状态**（维护中 / 仅修复 / 已归档）回答"承诺到哪一天"。
- 组合示例：`1.20.4` = 必出包 + 维护中（**常驻基线**，永不归档）；`1.21.4` = 仅声明 + 未激活（还没进生命周期）；`1.20.6` 将来可以变成"必出包 + 仅修复"。

### 1.3 降档触发条件（数字化，满足任一条即降档）

| # | 触发条件 | 判定方式 | 降到 |
|---|---|---|---|
| 1 | 上游依赖不再提供可用坐标 | Modrinth `game_versions` / maven-metadata 查不到该 MC 的 release | **已归档**（直接跳档） |
| 2 | 映射停止更新（该 MC 不再有 Yarn build） | `meta.fabricmc.net/v2/versions/yarn/<mc>` 为空 | 已归档（若要继续支持，须走 26.x 式"无映射独立节点"，成本另算） |
| 3 | 连续 **2 个 MC 大版本周期**（约 6 个月）无 issue、无玩家反馈 | 人工确认 | 仅修复 |
| 4 | 构建成本失控：活跃节点 ≥ 8 且并行 remap 反复 OOM | Gradle 日志 | 归档**最老的非基线**版本（`1.20.4` 永不动） |
| 5 | 第三方功能整代不可用（如某版本 Xaero 无坐标且无法退化为禁用） | `25` 号文档的矩阵 | 仅修复（README 标注缺失项） |

### 1.4 下线动作清单（按顺序执行，缺一不可）

1. 从 `settings.gradle` 的 `versions()` 列表移除该版本（**这是唯一的"下线"开关**）。
2. 从 `25-发布配置与产物矩阵.md` 的"必出包"移到"仅声明/历史"栏，并注明最后产物与日期。
3. 更新 README 的支持矩阵（"计划支持"→"不再支持"）。
4. 从冒烟清单（`25` 第五节）里移除该版本的特有项，避免无效测试。
5. **保留 `versions/<版本>/` 目录与全部源码**（09 Task2 Step4：归档 ≠ 删代码），只在本文 §1.6 里记一行状态。
6. `gradle.properties` 的 `deps.<版本>.*` **保留不删**：重新激活时不用重新调研坐标，只需把它放回 `versions()`。
7. 不要删 `probe-logs/` 里该版本的历史清单与日志。

### 1.5 重新激活（反向动作，比下线更常见）

把版本放回 `versions()` → 跑一次 `.\gradlew.bat :<版本>:build` → 跑三件套 → 若坐标过期（上游发过新版）先按第三节 SOP 更新 `deps.<版本>.*`。

## 二、固定动作清单

### 2.1 每次上游发版后做什么（按触发源）

| 触发源 | 检查什么 | 怎么查 | 判定与动作 |
|---|---|---|---|
| Minecraft 出新版本 | Yarn 是否已有 build | `meta.fabricmc.net/v2/versions/yarn/<mc>` | 有 → 走第三节 SOP；无 → 等 |
| Yarn 同 MC 出新 build | 是否值得跟 | 同上 | 只在需要新 API/修 bug 时跟；改 `deps.<v>.yarn` 后单节点构建 |
| Fabric Loader 发版 | 是否要提高 `fabric.mod.json` 下限 | `gradle.properties` / 11 号矩阵 | **只记录不主动追**（会动产物与 manifest） |
| Fabric API 发版 | 是否修了我们踩的坑 | Modrinth | 有价值 → **先汇报**；换值会动产物，需重设基线口径 |
| ModMenu / Xaero / BlueMap / LuckPerms 发版 | 是否覆盖目标 MC | Modrinth `game_versions` / maven-metadata | 覆盖 → 更新 `deps.<v>.<name>`，**必须编译实测**（见 3.5 坑 3） |
| JDK 发版 | 依赖字节码版本 vs 节点 Java | `javap -v` 看 class major | 依赖更高 → 必须换 `deps.<v>.java`（11 号矩阵 §四） |
| 我们自己发版 | 全量回归 | 见 2.2 | 升 `mod_version` → 全节点构建 + 三件套 + 逐包元数据核对 |

### 2.2 每次改动收尾必跑的三件套（顺序固定）

```powershell
# 1) 全节点构建（当前 4 个节点；出错先单节点复现）
.\gradlew.bat build --console=plain

# 2) D1 基线门禁（必须 RESULT: PASS）
pwsh -NoProfile -File docs/plans/multiversion/tools/verify-baseline.ps1 -AllowChanged 'areahint/'

# 3) 协议两张网（必须在提交前跑，见下方陷阱）
pwsh -NoProfile -File docs/plans/multiversion/tools/verify-channels.ps1
pwsh -NoProfile -File docs/plans/multiversion/tools/verify-protocol.ps1
```

**必须知道的陷阱**：`verify-channels.ps1` 与 `verify-protocol.ps1` 都用 `git diff --name-only HEAD -- src` 决定比对范围，是"HEAD vs 当前工作区"的对比。**一旦 commit，HEAD 就变成你刚提交的内容，两个脚本会自动变成"自己跟自己比"而永远 PASS**。所以：
- 提交前跑（Lead 统一提交，因此这两个脚本由 Lead 在提交前执行一次）；
- 提交后想复核，只能改成 `git diff --name-only HEAD~1 -- src`（或把比对基准做成参数）。

执行第五节的九项检查，把数字记到下面的"体检台账"，用于判断是否在退化。

| 日期 | 条件注释总数 | 单文件最高 | 越界 import | 真实旧网络 API | 语言键 | 三件套 | 备注 |

## 三、新增一个版本节点的标准作业流程（SOP）

### 3.0 决策树：这个版本要不要新建实现文件

```text
新版本 V
  |
  +-- Q1 V 落在已知世代吗？（查 3.2 世代表）
  |      +-- 落在 ---> 复用该世代的版本侧实现：把已有节点的 7/9 个类逐字复制到 versions/V/
  |      |             （同代际共享一套实现代码，但机制②要求"每个节点各一份"，见 3.4）
  |      +-- 不落在 -> Q2
  |
  +-- Q2 网络 API 换代了吗（1.20.5 式 CustomPayload / 26.x 式无映射）？
  |      +-- 是 ---> 写新的 NetworkCompatImpl + Payload 类（照抄相邻世代的实现再改）
  |      +-- 否 ---> 继续
  |
  +-- Q3 渲染/UI 换代了吗（1.21 式 Tessellator 移除 / 列表控件签名）？
  |      +-- 是 ---> 差异 <=3 行且单文件 ---> 条件注释（契约规则 3）
  |      |                       否则      ---> 新版本侧类（如 BufferCompat 式）
  |      +-- 否 ---> 大概率零改动，先构建看看
  |
  +-- Q4 映射换代了吗（Yarn -> 官方不混淆）？
         +-- 是 ---> 独立节点形态（独立脚本 / no-remap Loom），禁止在共享 src/ 写两套类名
```

### 3.5 已知坑速查（全部来自本仓库实测，新增版本时逐条对一遍）

| # | 坑 | 现象 | 处理 |
|---|---|---|---|
| 1 | 版本目录里放了与共享 `src/` 同名的类 | `错误: 类重复: areahint.XxxYyy` | 机制 ②：不同 FQN；或整体 `setSrcDirs` 替换（`18` 号文档） |

## 四、映射切换（Yarn → 官方名）长期预案

### 4.1 规则（硬性）

1. **映射不同代的版本不共用同一份 `src/` 类名体系**：26.x 的类名是官方名，与 Yarn 名成体系不同。
2. 26.x 必须以**独立节点形态**维护（独立 settings / 独立 buildscript + no-remap Loom + JDK 25），**禁止在共享 `src/` 里写两套类名**（`06` 号文档已明令）。
3. 共享 `src/` 的 267 个文件在 26.x 上要么整体改名（不现实），要么不参与编译（独立骨架 + 版本侧实现）。

### 4.3 迁移顺序建议（真要开 26.x 时照这个次序）

# A-1 条件注释：总数 / 文件数 / 单文件分布
$f = Get-ChildItem 'src' -Recurse -File -Filter *.java
$c = $f | Select-String -Pattern '//\s*\?'
"cond_total=$($c.Count) files=$(($c | Select-Object -ExpandProperty Path -Unique).Count)"
$c | Group-Object Path | Sort-Object Count -Descending | ForEach-Object { "{0}|{1}" -f $_.Count, $_.Name }

# A-2 每个节点的版本侧类数量
Get-ChildItem 'versions' -Recurse -File -Filter *.java |
  Where-Object { $_.FullName -notmatch '\\(build|bin|\.gradle|skeleton)\\' } |
  Group-Object { ($_.FullName -replace '.*\\versions\\([^\\]+)\\.*','$1') } |
  ForEach-Object { "{0}: {1}" -f $_.Name, $_.Count }

# A-3 第三方越界 import（三个数字）
$f | Select-String -Pattern '^\s*import\s+(static\s+)?xaero\.' | Measure-Object | Select-Object -ExpandProperty Count
$f | Select-String -Pattern '^\s*import\s+(static\s+)?de\.bluecolored\.' | Measure-Object | Select-Object -ExpandProperty Count
$f | Select-String -Pattern '^\s*import\s+(static\s+)?net\.vulkanmod' | Measure-Object | Select-Object -ExpandProperty Count
