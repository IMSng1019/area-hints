# 总纲与约定（每个阶段动手前先读这一份）

> 一句话方案：**Stonecutter 负责「构建编排 + 机械改名」，NetworkCompat 负责「网络层深断点（就这一个抽象层）」，物理隔离负责「让绝大多数文件不需要任何条件块」。**
>
> **状态：阶段 0 已实测完成。** 结论见 `10-阶段0-探针结论.md`、`17-第二真实编译目标验证.md`、`18-受控实验-版本目录编译语义.md`。第 3.5 节是**已定稿决策**，不要再讨论。

## 一、总体形态

**只有一个 main 分支，一个仓库。** 不新建分支、不建 worktree。多版本靠 **main 上的目录分层**实现：

```
main
├── settings.gradle / stonecutter.gradle / gradle.properties   ← 版本编排与每版本参数
├── src/                    ← 共享内核：接口 + 绝大多数业务代码
│   ├── main/java/areahint/
│   ├── client/java/areahint/
│   ├── main/resources/
│   └── client/resources/
└── versions/               ← 每个小版本一个文件夹，是独立构建目标
    ├── 1.20.4/             ← 常驻基线；该版本的依赖参数与产物
    ├── 1.20.1/             ← 第二真实目标（src/main 零改动，仅 16 处客户端 UI 差异，见阶段 4）
    ├── 1.21.1/             ← 跨代际目标；NetworkCompat 完成前保持空骨架
    └── ...
```

**空文件夹不是浪费**：它承载「该版本的依赖版本、Java 工具链、产物元数据」，并产出独立 jar。

### 1.1 `versions/<v>/` 的真实语义（实测结论，必须遵守）

| 情况 | 结果 |
|---|---|
| 版本目录属于**已声明节点**，且与共享 `src/` 有**同名同路径**的类 | `错误: 类重复`，构建失败 |
| 版本目录属于**未声明节点** | 完全不参与任何编译 |
| 版本目录里的类与共享 `src/` **无同名**（不同 FQN） | 正常编译并进入该节点产物 |

结论：**Stonecutter 把它当作「追加编译」，没有覆盖语义。** 版本目录只能放共享源码里不存在的新类，或配合显式 `setSrcDirs` 做整体替换。

## 二、三层职责，不许混用

| 层 | 职责 | 判定 |
|---|---|---|
| Stonecutter | 从一棵树产出多个版本的 jar；用条件注释做**机械改名**与 ≤3 行小差异 | 出现「整块实现不同」时，不许硬塞条件注释 |
| NetworkCompat | 只抽象网络 API 的**形状**，不抽象协议 | 除它以外，不允许再建第二个通用抽象层 |
| 物理隔离 | 让 `src/` 里绝大多数文件零条件块 | `src/` 里新出现的条件注释必须有理由 |

### 2.1 物理隔离机制（已定稿：机制 ②）

**定义**：`src/` 只保留**接口**（零 `net.minecraft.*` import）；每个版本把**实现**放在自己的 `versions/<版本>/` 目录里，**类名互不相同（不同 FQN）**。共享侧通过接口调用，调用点不需要任何条件注释。

为什么必须是「不同 FQN」而不是「同名覆盖」：见 1.1 的实测表——同名即冲突。

样例（以 `Packets` 里的 `new Identifier(...)` 为例）：

```
src/main/java/areahint/network/
├── Packets.java          ← 保留：通道名字符串、维度常量、映射方法（与 MC API 无关）
└── Identifiers.java      ← 新增接口：id(String path)；零 MC import

versions/1.20.4/src/main/java/areahint/network/Identifiers1204.java   ← new Identifier(MOD_ID, path)
versions/1.20.1/src/main/java/areahint/network/Identifiers1201.java   ← new Identifier(MOD_ID, path)
versions/1.21.1/src/main/java/areahint/network/Identifiers1211.java   ← Identifier.of(MOD_ID, path)
```

编译映射：`:1.20.4` 只看得见 `Identifiers1204`，`:1.21.1` 只看得见 `Identifiers1211`——任意两个同名类不会进入同一次 javac，因此不冲突。

**唯一交接点**是「共享侧怎么知道 new 哪个实现」（实现类名在别的版本里不存在）。三种接法，按优先级：

1. **每个版本目录各放一个同名工厂类**（最干净：每个节点只挂载一个版本目录，不会冲突）；
2. 入口处集中写 2–3 行条件注释（可接受，入口只有一个）；
3. 反射用字符串类名（不推荐，丢失编译期检查）。

**禁止清单**：

- 不许在 `src/` 放与任何版本目录同名的类；
- 不许把业务逻辑（`*VisualController`、`*Manager`、`*UI`）搬进 `versions/`——它们应通过接口消化差异；
- 不许用机制 ② 去处理「≤3 行的机械改名」——那种用条件注释更省事（见阶段 5）。

## 六、硬性禁止项（每个阶段都适用）

1. **不写任何测试** —— 我会自己进游戏测试。
2. **不创建分支、不创建 worktree、不 `git commit`** —— 直接在 main 上修改。
3. 不改 `build/`、`run/` 等生成目录。
4. 不夹带功能改动：本系列只保证「多版本能编译并运行」，不顺手改行为、不重构无关代码。
5. 不提出或执行任何部署/发布动作；产物只出到本地构建目录。
6. 注释一律用中文，单处注释尽量只占一行；代码结构尽量与原架构保持一致。
7. **不确定就停下汇报**，不要自行降级方案、不要猜依赖坐标。
8. **第三方依赖必须按版本解析**（D2）：只改 `minecraft`/`yarn`/`fabric` 而不改 ModMenu / Xaero，会编过但**运行时加载失败**（实测：1.20.1 节点编的是 1.20.4 的 ModMenu 9.2.0，其 fabric.mod.json 声明 minecraft >=1.20.3）。
