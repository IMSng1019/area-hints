# editviz 坐标精度与边界简化实施计划

**目标：** 新生成坐标按 0.1 格量化，简化后轮廓相对操作前原始轮廓的偏移最多 1 格，量化误差计入该限额。初版采用 0.5 格，随后按用户要求调整为 1 格。

**架构：** 绘制结束时只优化新增边界，保留旧边及交点的原始精度；显式“简化边界”按钮处理当前完整边界。按用户后续要求，提交核对前再整体优化当前目标并强制全部顶点一位小数，服务端对主顶点和二级顶点统一校验、编码。最终顶点缓存于可撤销草稿，使画布、审批预览和保存值一致。

**技术：** Java 17、Java2D Area、多版本 Fabric Screen、现有 11 种语言与 Gradle 验证。

## 实施步骤

1. 在 `src/main/java/areahint/vizedit/geometry/` 实现有误差上限、旧边保护和复杂度限制的轮廓优化。不得改变 `validate`、`union`、`subtract` 的既有语义；无法安全简化则保留原形状。
2. 在 `src/client/java/areahint/vizedit/VizEditScreen.java` 接入笔画完成、魔棒和显式按钮，复用草稿历史；按实际面积差检查界面权限，服务端继续重新检查。显示简化前后点数。
3. 更新全部语言的按钮、提示、结果文本，以及 `COMMAND_USAGE.md`。
4. 按用户要求不新增测试文件；运行现有测试、五版本构建、翻译键检查及 `git diff --check`，执行独立代码审查。

## 验收要点

- 长斜线与椭圆的阶梯顶点减少，保存后重新打开与简化预览一致。
- 绘制阶段保留负坐标、大坐标及旧小数斜边；按最新保存规则，提交核对前连同旧边和交点统一量化至一位小数，普通属性编辑后保存也执行。
- 显式简化可撤销、重做，状态提示显示前后点数；只读、失效、等待提交时不可操作。
- 洞、不连通及自交不能被简化悄悄修复；细窄连接保留，不能安全量化的边界保留原样。
- 缺少扩张或缩小权限时，不额外引入需要该权限的几何变化。
- 两种画布、审批草稿、鼠标释放和离开画布的交互需游戏内人工验收；构建通过不代表这些项目已完成。

## 保存前整体优化与严格一位小数

用户进一步明确要求保存时整体优化、所有保存点强制一位小数，因此保存阶段不再保留旧边或交点的高精度例外；绘制阶段的旧边保护仍保留。

实施内容：

1. `VizEditGeometry.prepareForSave` 返回经过原环校验、全轮廓简化和一位小数量化的确切顶点列表；失败只能退到合法的一位小数原轮廓，不能退回高精度数据。
2. 客户端在进入提交核对前准备最终草稿并记录撤销；缓存确切顶点及对应形状，几何未变时重复核对不再次简化。提交超时重试仍使用原请求，删除不优化坐标。
3. `VizEditVertexFormat` 使用一位小数的 JSON 数字编码，整数也写成 `10.0`；服务端先检查原输入，再量化并复验，主顶点和二级顶点统一格式。服务端不重复有损简化，以免预览和审批轮廓漂移。
4. 旧高精度审批申请需要重新编辑并提交；当前目标的实际面积增减继续检查对应权限，不批量优化无关域名或只涉及父引用、等级联动的后代。
5. 更新 11 种语言的保存提示和命令文档，按用户要求不新增测试文件。

本次 `./gradlew.bat build --no-parallel --console=plain` 五版本构建及现有测试通过，耗时 38 秒。11 种语言各有 2570 个键、91 个编辑器键，翻译检查通过；差异检查和独立代码审查通过。未新增测试文件。

通过 JShell 调用实际编译后的几何、客户端草稿及服务端变更代码，确认：

- 高精度旧坐标保存为 `-3.2`、`7.4` 等一位小数；整数和大坐标写成 `10.0`、`30000000.0`，均为 JSON 数字。
- 量化后退化的细窄多边形与含洞草稿分别被拒绝，没有回退到长小数保存。
- 200×100 格椭圆准备保存后得到 35 个确切顶点；只改属性后重复准备、复制草稿时提交顶点完全一致，重新绘制后缓存会重新生成。
- 服务端输出的主顶点、二级顶点均为一位小数；审批依赖重放结果逐字相同；只有 rename 权限但量化产生面积变化时，整笔修改被拒绝。

游戏内尚需检查仅改名或颜色时的自动优化、保存失败时草稿保留、返回画布后的重复核对、撤销重做以及审批打回重提。
