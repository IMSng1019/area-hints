## 三、构建脚本改动方案（diff 片段，待 Lead 统一应用）

### 3.1 产物命名：加 `+MC` 后缀

**目标**：`areas-hint-fabric-4.6.0+1.20.4.jar`（平台段 `-fabric-` 保留，便于将来 Forge/NeoForge 同仓库出包）。
若要求与 08 文档字面完全一致（`areas-hint-4.6.0+1.20.4.jar`），把 `artifactBaseName` 里的 `-${modLoader}` 去掉即可；二选一，本文推荐保留平台段。

`build.gradle` 提案（当前 75、80-85 行附近）：

```diff
-version = project.mod_version
+// 产物版本号带上目标 MC：4.6.0+1.20.4（阶段 7 Task2 Step1）
+// 实验性档位再加 -experimental（阶段 7 Task3 Step2，见 3.3）
+def releaseChannel = (project.findProperty("deps.${mcVersion}.channel") ?: 'stable').toString()
+version = releaseChannel == 'experimental'
+        ? "${project.mod_version}+${mcVersionDep}-experimental"
+        : "${project.mod_version}+${mcVersionDep}"
 
 // 模组平台标识：默认 Fabric，移植到 Forge/NeoForge 时在 gradle.properties 里改 mod_loader
 def modLoader = (project.findProperty("mod_loader") ?: "fabric").toString().trim().toLowerCase(Locale.ROOT)
-// 产物基础名：模组名-平台-MC版本，Gradle 会再拼上 mod_version，最终形如 areas-hint-fabric-1.20.4-4.6.0.jar
-def artifactBaseName = "${project.archives_base_name}-${modLoader}-${mcVersionDep}"
+// 产物基础名：模组名-平台；MC 版本已经进 version，最终形如 areas-hint-fabric-4.6.0+1.20.4.jar
+def artifactBaseName = "${project.archives_base_name}-${modLoader}"
 ```

**连带影响（必须一起处理）**
1. `sourcesJar` 名字同步变成 `areas-hint-fabric-4.6.0+1.20.4-sources.jar`（自动跟随 `version`）。
2. `publishing` 的坐标版本变成 `4.6.0+1.20.4`（每节点一份，互不覆盖）——**本阶段仍然不 publish**。
3. `tools/verify-baseline.ps1` 默认路径要改（见 3.7）。
4. **基线门禁不受影响**：`verify-baseline.ps1` 比对的是 jar **内部条目名**，与 jar 文件名无关；只要 3.2 采用方案 A，`fabric.mod.json` 内容不变。

### 3.2 `fabric.mod.json` 的 `version`：两个方案

**方案 A（推荐）：jar 名带 `+MC`，元数据 `version` 保持 `4.6.0`**

`fabric.mod.json` 提案：

```diff
-	"version": "${version}",
+	"version": "${mod_version}",
```

`build.gradle` 的 `processResources` 提案（当前 175-191 行）：

```diff
 processResources {
 	inputs.property "version", project.version
+	// fabric.mod.json 的 version 只跟模组版本走，不跟产物名的 +MC 后缀走（保住 D1 基线）
+	inputs.property "modVersion", project.mod_version
 	…
 	filesMatching("fabric.mod.json") {
 		expand "version": inputs.properties.version,
+			"mod_version": inputs.properties.modVersion,
 			"minecraft_range": minecraftRange,
```

**为什么推荐 A**：改完后 `fabric.mod.json` 的内容与今天**逐字节相同**，`verify-baseline.ps1 -AllowChanged 'areahint/'` 继续 **PASS**（铁律 2 不动摇）。代价是"文件名 4.6.0+1.20.4、元数据 4.6.0"，需要在 README 里说明两者关系。

**方案 B：元数据也带 `+MC`**（`fabric.mod.json` 模板不动，`version` 展开为 `4.6.0+1.20.4`）
- 优点：游戏内 ModMenu/日志显示的版本与文件名一致。
- 代价：`fabric.mod.json` 条目内容变化 → 基线核对必须放宽为 `-AllowChanged 'areahint/|fabric.mod.json'`，并把这次变化**明确记账**（属于"有意的元数据变更"，不是回归）。
- 需 Lead 拍板；未拍板前按方案 A 落地。

### 3.3 「实验性版本要在产物里标注」的三层落地

| 层 | 做法 | 效果 |
|---|---|---|
| 文件名 | 3.1 的 `releaseChannel` → `areas-hint-fabric-4.6.0+26.1-experimental.jar` | 下载页/文件夹里一眼可辨 |
| 元数据 | `fabric.mod.json` 增加 `custom` 与名称后缀（见下） | 游戏内与外部分析工具都能读到 |
| 文档 | README + `11-版本矩阵.md` 的档位列 | 用户下载前就知道 |

`fabric.mod.json` 提案（新增 `custom` 段）：

```diff
 	"name": "Area Hints - 域名${release_name_suffix}",
 	…
 	"depends": { … },
+	"custom": {
+		"areas-hint:release_channel": "${release_channel}",
+		"areas-hint:target_mc": "${target_mc}",
+		"areas-hint:build_note": "${release_note}"
+	},
 	"suggests": { … }
```

`build.gradle` 侧只需把三个值塞进 `expand` 与 `inputs.property`：

```groovy
// 实验性标注：产物元数据里写明"仅编译验证"（阶段 7 Task3 Step2）
def releaseChannel = (project.findProperty("deps.${mcVersion}.channel") ?: 'stable').toString()
def releaseNameSuffix = releaseChannel == 'experimental' ? ' [实验性 / Experimental]' : ''
def releaseNote = releaseChannel == 'experimental'
        ? '仅编译验证，未进游戏测试；第三方模组可能缺失'
        : ''
```

`gradle.properties` 侧（新增键，缺省 `stable`）：

```properties
# 发布通道：stable（默认，可省略）/ experimental（产物名与元数据都带实验性标注）
deps.26.1.channel=experimental
deps.26.2.channel=experimental
```

> 注意：26.x 目前**没有**生效的 `deps.26.1.*` 官方坐标（只有注释形态，见 `gradle.properties:147-161`）；真正激活时要连坐标一起补。

### 3.5 一键聚合构建

**路线 1（零脚本改动，今天就能用）**：

```powershell
# 全部已声明节点（当前 4 个）
.\gradlew.bat build --console=plain
# 只构建稳定档（当前等价于全部，因为实验档不进 versions()）
.\gradlew.bat :1.20.4:build :1.20.1:build :1.20.6:build :1.21.1:build --console=plain
# 将来单独出实验档（临时激活后）

```

**路线 2（可选，脚本聚合任务）**：`build.gradle` 末尾追加（根项目守卫，避免每个节点各注册一次）：

```groovy
// 聚合构建：稳定档与实验档分开，实验档失败不阻塞正式产物（阶段 7 Task1 Step2）
if (project == rootProject) {
	def stableNodes = ['1.20.4', '1.20.1', '1.20.6', '1.21.1']
	def experimentalNodes = ['26.1', '26.2']
	tasks.register('buildStable') {
		group = 'build'
		description = '构建全部正式档位节点'
		dependsOn stableNodes.collect { ":${it}:build" }
	}
	tasks.register('buildExperimental') {
		group = 'build'
		description = '构建实验性档位节点（未激活时为空操作）'
		dependsOn experimentalNodes.findAll { findProject(":${it}") != null }.collect { ":${it}:build" }
	}
}
```

- 落地后必须验证一次：`.\gradlew.bat tasks --group build --console=plain` 能看到两个任务；`.\gradlew.bat buildStable` 退出码 0。
- 若 Stonecutter 对根项目脚本的求值方式导致任务重复注册，**退回路线 1**（不改脚本），不要在这上面纠缠。

## 四、产物核对：命令与期望值

每个版本出包后**逐包**执行（这是 08 Task2 Step2 的"不许只看构建脚本"）：

```powershell
# 逐包读取 fabric.mod.json 的关键字段（只读，不需要 gradle）
Add-Type -AssemblyName System.IO.Compression.FileSystem
Get-ChildItem 'versions/*/build/libs/*.jar' | Where-Object { $_.Name -notlike '*sources*' } | ForEach-Object {
  $zip = [System.IO.Compression.ZipFile]::OpenRead($_.FullName)
  $e = $zip.Entries | Where-Object { $_.FullName -eq 'fabric.mod.json' }
  $sr = New-Object System.IO.StreamReader($e.Open()); $o = ($sr.ReadToEnd() | ConvertFrom-Json); $sr.Close()
  $n = $zip.Entries.Count; $zip.Dispose()
  "{0} | entries={1} | version={2} | mc={3} | java={4} | xaero={5}/{6}" -f $_.Name, $n, $o.version, $o.depends.minecraft, $o.depends.java, $o.suggests.xaerominimap, $o.suggests.xaeroworldmap
}
```

**判定标准**：`mc` 必须以 `~<该节点 MC>` 结尾；`java` 必须与 `deps.<v>.java` 一致；`version` 与文件名符合 3.2 选定的方案；条目数 = 基线 456 + 该节点版本侧类产生的条目（当前 474/476）。
