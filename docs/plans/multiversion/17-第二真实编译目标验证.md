## 一、结论

**1.20.1 可以作为「第二个真实编译目标」：需要 16 处改动，全部落在 `src/client`（12 个文件），`src/main` 一行都不用改。**

| 判定项 | 实测结果 |
|---|---|
| `src/main`（服务端 / 共享，含全部网络层） | **0 错误、0 改动**；59 个源文件全部编译，产出 **85 个 class，与 1.20.4 节点的 `src/main` class 数完全相同（85 vs 85）** |
| `src/client`（客户端） | **16 条错误 / 12 个文件**，全部是原版客户端 UI 与文本序列化 API 差异，**没有一条涉及网络层或 `HudRenderCallback`** |
| 网络层（`PacketByteBuf` 156 处 / `ServerPlayNetworking` 77 处 / `ClientPlayNetworking` 84 处） | 一行都不用改 |
| HUD 渲染（`HudRenderCallback` 8 处 / 4 个渲染类） | 一行都不用改（`CPURender` / `GLRender` / `VulkanRender` / `AddHintClientNetworking` 的 class 已成功产出） |
| Java 工具链 | 仍是 17，与 1.20.4 同一套 |
| 16 处里可写成「两版通用」的 | **6 处**（A 4 处 + D 2 处），改完 1.20.4 上照样编译 |
| 16 处里必须分支的 | **10 处**（B 9 处 + C 1 处），需要 Stonecutter 条件注释或一个极小的兼容封装 |

一句话：**1.20.1 与 1.20.4 的差距不在「代际」，而只在 1.20.2–1.20.4 期间的原版客户端 UI / 文本 API 演进；网络层与渲染回调在整个 1.20.x 上同形态。**

### 3.4 `src/main` 与 `src/client` 的区分（第 2.4 步）

- **`compileJava`（`src/main`）成功执行且零输出**：没有错误、没有警告。日志里 `> Task :1.20.1:compileJava` 之后直接是 `processResources`。
- 覆盖度证明：Stonecutter 生成的 `versions/1.20.1/build/generated/stonecutter/main/java` 有 **59** 个 `.java`，与 `src/main/java` 的 **59** 个逐一对应；产出 `build/classes/java/main` **85 个 class**，与 1.20.4 节点 `src/main` 的 **85 个 class** 数量相同。
- **`compileClientJava` 失败**（16 条），因此 `compileJava` 之后的 `remapJar` / `jar` 未执行，1.20.1 节点**没有产出 mod jar**，只产出了 `versions/1.20.1/build/libs/areas-hint-fabric-1.20.1-4.6.0-sources.jar`（`remapSourcesJar` 成功，说明 Loom 管线本身健康）。
- 客户端 source set 共 **199** 个源文件（生成目录同样 199），报错只涉及其中 **12 个**；javac 在本次构建中仍写出了 **22 个客户端 class**（时间戳与本次构建一致），其中包含**全部 4 个 `HudRenderCallback` 使用者**与客户端网络族：
  `areahint/render/CPURender.class`、`GLRender.class`、`VulkanRender.class`、`addhint/AddHintClientNetworking.class`、`AreashintClient.class`、`detection/AreaDetector.class` 等。
  → 这是除 javap 之外的**第二重证据**：客户端网络层与 HUD 渲染层在 1.20.1 上确实编得过。

## 五、与 1.20.6 的对比：数量级差异说明什么

| 维度 | **1.20.1**（本轮） | **1.20.6**（阶段 0 探针 C） |
|---|---|---|
| `src/main` 错误 | **0**（59/59 文件编译，85 个 class 与 1.20.4 相同） | **61**（`compileJava` 直接失败） |
| `src/client` 错误 | **16**（`compileClientJava` 执行了，报错全在客户端） | 未执行（`compileClientJava` 依赖 `compileJava`；单独跑复现同一批 main 错误），客户端网络族断点靠 javap 单独确认 |
| 断点性质 | 原版**客户端 UI / 文本** API（`Screen` / `ElementListWidget` / `Text` / `ClickableWidget`） | **网络层整代改造**（`CustomPayload` + `PacketCodec`）+ `ServerWorld.getDimensionKey()` 移除 |
| 网络 API | `send(Player,Identifier,PacketByteBuf)` / `registerGlobalReceiver(Identifier,…)` **完全同形态** | 两种旧形态**均已不存在** |
| Java | 17（与 1.20.4 同一工具链） | 21（需要第二套工具链） |
| 版本号跨度 | 相差 3 个小版本（1.20.1 → 1.20.4） | 相差 2 个小版本（1.20.4 → 1.20.6） |
| 结论 | **可当第二个真实目标**（成本 16 处客户端 UI） | **不能**，必须等 NetworkCompat 落地 |

**这说明的是：分界线是「代际」（1.20.4 → 1.20.5 的网络层重写、1.21 的渲染重写），不是「版本号差多少」。** 1.20.6 只差 2 个小版本却出 61 条网络层错误；1.20.1 差 3 个小版本却 0 条网络层错误。因此：

- 第二目标选同代际版本，才能真正起到「多目标编排不回归」的量尺作用；
- 1.20.6 那 61 条只能靠 NetworkCompat 解决，与第二目标的选择无关，不该混在一起做。

## 六、对阶段 0 / 阶段 1 的建议

1. **阶段 0 的第二个真实目标：选 1.20.1。** 它是唯一在实测中让 `src/main`（含 156 处 `PacketByteBuf`、77 处 `ServerPlayNetworking`）**零改动编过**的非 1.20.4 版本，且 16 条断点**没有一条与阶段 1 的 NetworkCompat 抢同一批文件**（16 条全在客户端 UI 屏；NetworkCompat 的战场是 `src/main` 与客户端网络包，二者交集为 0）。
2. **验收口径要改**：如果仍要求「第二个目标必须 0 改动编译」，则 1.20.1 也不达标（16 处）。建议改成：**「第二目标 = 1.20.1，允许 ≤16 处客户端 UI 适配，且适配必须落在阶段 4（渲染/UI 跨版本适配）里，不许在阶段 0 做」**；阶段 0 的验收仍保持「工具链 + 依赖解析 + 节点产物」三项。
3. **`1.20.6` 继续留在注释里当红灯量尺**（探针 C 已如此处理），不要因为 1.20.1 通过就顺手打开它。
4. **第三方依赖必须按版本解析（阶段 1 Task 2 Step 4 的硬需求）**：1.20.1 需要 ModMenu **7.2.2**（9.2.0 的 `fabric.mod.json` 写明 `"minecraft": ">=1.20.3"`，1.20.1 运行时会被加载器拒绝）与 Xaero 的 **`_Fabric_1.20`** 变体（`25.2.0_Fabric_1.20` / `1.39.2_Fabric_1.20`）。当前 `build.gradle` 只用扁平键 `modmenu_version` / `xaero_*`，所以 1.20.1 节点编的是 1.20.4 的 jar——**编译能过、运行时会崩**，这一步必须在阶段 1 补上（本轮按要求未改 `build.gradle`）。
5. **1.20.1 在阶段 1 矩阵里应归「必出包」**：官方依赖齐（Yarn / Loader / Fabric API 全有），第三方 ModMenu 与 Xaero 都有对应坐标，只需在矩阵里写明版本降级（ModMenu 9.2.0 → 7.2.2，Xaero 1.20.4 → 1.20）。
