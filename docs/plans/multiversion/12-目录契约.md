## 二、五条规则（每条：条文 → 判定 → 本仓库正例 → 本仓库反例 → 落地动作）

### 规则 1：`src/` 是共享内核

**条文**：`src/` 下的文件不允许 import `net.minecraft.*`；渲染可视化控制器这类纯业务编排队除外（见规则 4）。
**判定方法（03 原文）**：一个文件如果没有 Minecraft API 依赖，它就不该有任何版本分支。

**本契约采用的落地口径**（由 00 第 2.1 节 + 03 规则 1 合并得出，避免"206 个文件全部违规"这种无法执行的读法）：

| 层 | 允许 import MC？ | 允许出现在 `versions/`？ | 现状 |
|---|---|---|---|
| (a) 纯逻辑 / 接口层：几何、JSON、颜色、数据模型、以及**所有 `src/` 接口** | **不允许** | 不允许 | 57 个文件（首轮 52；阶段 3 新增的 5 个接口载体都是零 MC import） |
| (b) 业务编排 / UI 层：`*VisualController`、`*Manager`、`*UI`、命令流程 | 允许 | **不允许**（规则 4） | 206 个文件里的大多数 |
| (c) 版本敏感的实现 | —— | **只允许放这里** | `src/` 里目前为 0 |

越界的两种形态：**(a) 类文件带了 MC import**（本阶段可清理，见 `13-越界引用清单.md`）；**(b) 类文件把版本敏感实现写死**（阶段 3/4 靠接口消化）。

**正例（真实文件）**
- `src/main/java/areahint/geometry/PolygonGeometry.java`：全文只 import `areahint.data.AreaData` 与 `java.util.*`，耳切法三角剖分与 MC 无关，永远不需要版本分支。
- 同类的还有 `src/main/java/areahint/file/JsonHelper.java`、`src/main/java/areahint/util/ColorUtil.java`、`src/main/java/areahint/data/AreaData.java`、`src/main/java/areahint/data/ConfigData.java`、`src/main/java/areahint/file/FileManager.java` 等，共 **57** 个零 MC import 文件（首轮 52；完整清单见附录 A-3）。

**反例（真实文件）**
- `src/main/java/areahint/network/Packets.java`：180 行里唯一的 MC 依赖是第 4 行 `import net.minecraft.util.Identifier;`，用途只是第 12–118 行的 **52 个 `Identifier` 常量**；其余全是纯字符串常量（`DIMENSION_OVERWORLD` 等）与纯函数（`convertDimensionPathToType` / `getFileNameForDimension`）。这就是"本该没有版本概念、却背着 52 处版本债"的典型。
- 次级反例（整文件只有 `Identifier` 一个 MC import，共 4 个）：`src/main/java/areahint/network/Packets.java`、`src/client/java/areahint/util/DimensionIdCache.java`、`src/client/java/areahint/log/AreaChangeTracker.java`、`src/client/java/areahint/soundevent/DomainSoundTracker.java`——后三个只是把 `Identifier` 当"维度引用 / 缓存 key"传递（例如 `DimensionIdCache.java:14` 的 `private static volatile Identifier cachedIdentifier;`）。

**落地动作**：这四个文件是阶段 3 的**第一批转接口对象**；除此之外，(a) 类文件**不得**再新增 MC import。

### 规则 2：`versions/` 只放「不同 FQN 的实现」

**条文**：某个能力在各版本间整块实现不同时，`src/` 只保留接口，实现在 `versions/<该代际最低版本>/` 下写一份，同代际其它版本目录留空。
**硬约束（阶段 0 实测）**：版本目录里的类**不得**与共享 `src/` 中任何类同名同路径——同名即 `错误: 类重复`。
**类名约定**：带版本后缀便于辨认，如 `Identifiers1204` / `Identifiers1211`。

**真实位置语义（必须先分清，否则文件会放错地方）**

| 节点类型 | 判定依据 | 手工实现放哪 |
|---|---|---|
| 非骨架节点（当前只有 `1.20.4`） | `deps.1.20.4.skeleton=false` | `versions/1.20.4/src/main/java/...`、`versions/1.20.4/src/client/java/...`（Stonecutter 自动挂载节点自己的 `src/`，探针 B-1 证据） |
| 骨架节点（当前只有 `1.21.1`） | `deps.1.21.1.skeleton=true` | `versions/1.21.1/skeleton/main/java/...`、`versions/1.21.1/skeleton/client/java/...`（`build.gradle:112-119` 用 `setSrcDirs` 整体替换了 source set） |

**正例（真实文件）**
- `versions/1.21.1/skeleton/main/java/areahint/skeleton/SkeletonCommon.java`（FQN `areahint.skeleton.SkeletonCommon`）与 `versions/1.21.1/skeleton/client/java/areahint/skeleton/SkeletonClient.java`：与共享 `src/` 中任何类都不同名，1.21.1 产物里确实含这两个类（阶段 0 探针 A-5 实测）。
- **机制 ② 的首个真实落地（阶段 3 Task 1/2 第一部分，commit `bbd171e`）**：`versions/1.20.4/src/main/java/areahint/network/` 与 `versions/1.20.4/src/client/java/areahint/network/` 下放了该版本的网络实现，交接点是版本目录里的**同名工厂** `NetworkCompatFactory.java`（客户端 `ClientNetworkCompatFactory.java`）。这批实现类的 FQN 与共享 `src/` 全部不同名，首次验证了「非骨架节点用 `versions/<v>/src/` 放实现」这条路径；**具体实现类名在阶段 3 期间仍会增删，契约只固定"接口在 `src/` + 同名工厂在 `versions/<v>/`"这一形态**。

**反例（阶段 0 实测记录，文件已删但证据在库）**
- `src/client/java/areahint/VersionProbeMarker.java` + `versions/1.21.1/skeleton/client/java/areahint/VersionProbeMarker.java`（同名同路径）→ 构建失败：
  ```
  J:\mc\mods\src\client\java\areahint\VersionProbeMarker.java:7: 错误: 类重复: areahint.VersionProbeMarker
  ```
  日志：`docs/plans/multiversion/probe-logs/probeB1-override-test.log`。这是"同名即冲突"的唯一直接证据，也是机制 ① 被否决的原因。

**落地动作**：新建 `versions/<v>/` 实现类时，先 grep 共享 `src/` 有没有同名类；类名一律带版本后缀。

### 规则 3：条件注释只用于小差异

**条文**：单文件、单方法内、**≤3 行**的差异才允许用 `//? if`；超过就是信号——应该拆到 `versions/`。

**正例（真实代码，差异恰好 1 行）**
- `src/main/java/areahint/command/ServerCommands.java:1079`：`Identifier dimension = source.getWorld().getDimensionKey().getValue();`
  1.20.5 起 `ServerWorld.getDimensionKey()` 改名，探针 C 实测 1.20.6 上该类只报 **1 条**错误 → 单行机械改名，属"≤3 行"，阶段 5 用条件注释处理最省事。

**反例（真实代码，差异跨 4 个文件 8 处）**
- `HudRenderCallback` 集群，共 8 处 / 4 文件：
  - `src/client/java/areahint/render/CPURender.java:85`（注册）与 `:93`（`onHudRender(DrawContext, float)`）
  - `src/client/java/areahint/render/GLRender.java:63` / `:71`
  - `src/client/java/areahint/render/VulkanRender.java:61` / `:69`
  - `src/client/java/areahint/easyadd/EasyAddRecordingHud.java:26`（`HudRenderCallback.EVENT.register(EasyAddRecordingHud::render)`）
  1.21 起回调第二个参数由 `float` 变为 `RenderTickCounter`，`this::onHudRender` 方法引用直接失配 → 要在 4 个文件里写 8 处条件注释，**远超 3 行**：这是明确的"应拆 `versions/` 或接口"的信号（阶段 4 处理）。

**现状与红线**：`src/` 下 `//?` 命中 **0** 处（附录 A-4）。本阶段**不允许新增**任何条件注释（03 验收标准）。

### 规则 4：业务编排不进 `versions/`

**条文**：`*VisualController`、`*Manager`、`*UI` 这类只做业务编排的文件保持在 `src/`，版本差异通过调用接口消化。
**规模**：全仓库 `*VisualController` **48** 个、`*Manager` **36** 个、`*UI` **17** 个——它们是"必须留在 `src/`"的主体。

**正例（真实文件）**
- `src/client/java/areahint/command/OnVisualController.java`：42 行，只 import `MinecraftClient` 与 `Screen` 两个 MC 类，全靠 `CommandUiActions.runCommand("areahint on")` 与 `WizardConfirmScreen` 编排流程，零网络调用、零版本敏感 API → 放在 `src/` 是对的，任何版本都不需要它进 `versions/`。

**反例（真实文件，编排类里混进了版本敏感调用）**
- `src/client/java/areahint/render/RenderManager.java`：Manager 直接 import `net.minecraft.client.MinecraftClient`，并在 `:39-60` 用 `VulkanModCompat.isUsable()` 决定 CPU/OpenGL/Vulkan 后端。
- `src/client/java/areahint/recolor/RecolorManager.java`：Manager 里直接 4 处 `PacketByteBuf`、2 处 `ClientPlayNetworking`（见 `13` 第四节）。
**修法（关键）**：反例的处置**不是**把 Manager 搬进 `versions/`（那是规则 4 明令禁止的），而是把版本敏感调用抽成接口——阶段 3 的 NetworkCompat 与阶段 4 的渲染接口就是干这个的。

### 规则 5：共享侧怎么挑实现（交接点）

**条文**：实现类名在其它版本里不存在，因此共享侧不能写死。三种接法按优先级：
1. **每个版本目录各放一个同名工厂类**（推荐；每个节点只挂载一个版本目录，不会冲突）；
2. 入口处集中写 2–3 行条件注释（入口只有一个时可接受）；
3. 反射用字符串类名（**不推荐**，丢失编译期检查）。

**本仓库已有的"同形先例"（都是接法 3，且都是为可选依赖服务，可接受）**
| 文件 | 行 | 写法 |
|---|---|---|
| `src/client/java/areahint/xaero/XaeroCompat.java` | :42 | `Class.forName("areahint.xaero.minimap.XaeroMinimapBridge")` |
| `src/main/java/areahint/map/BlueMapCompat.java` | :35 | `Class.forName("areahint.map.BlueMapIntegration")`，并把实例收敛到接口 `BlueMapBridge` |
| `src/client/java/areahint/render/VulkanModCompat.java` | :48 | `Class.forName("net.vulkanmod.Initializer")` |

**注意**：上面三处先例解决的是"第三方模组没装时不能触发类加载"，不是版本差异；机制 ② 的实现类有编译期可见性，**推荐接法 1**（同名工厂）。

**接法 1 的真实落地（阶段 3 Task 1/2 第一部分，可直接照抄的范本）**

| 文件 | 行 | 作用 |
|---|---:|---|
| `versions/1.20.4/src/main/java/areahint/network/NetworkCompatFactory.java` | :6-14 | 版本目录里的**同名**工厂；文件注释直接写明"每个版本目录各放一份同名工厂，编译期每个节点只看得见自己那一份" |
| `src/main/java/areahint/network/NetworkCompat.java` | :22-33 | 共享接口的 `install(...)` / `get()`：静态持有者收在嵌套类 `Holder` 里 |
| `src/main/java/areahint/Areashint.java` | :90 | **全仓库唯一交接点**：`NetworkCompat.install(NetworkCompatFactory.create());` |
| `src/client/java/areahint/AreashintClient.java` | :91 | 客户端同形：`ClientNetworkCompat.install(ClientNetworkCompatFactory.create());` |

> 接口 `NetworkCompat` 的签名里保留了 `ServerPlayerEntity`（1.20.1–1.21.11 全程稳定的类型），这是**刻意的、已在代码注释里写明的例外**；各版本的缓冲区类型绝不进接口（见 `NetworkCompat.java:8-9`）。

## 四、"新文件该放哪"判定流程

```
新文件/新能力
  │
  ├─ Q1 它会出现 net.minecraft.* / Fabric API / 第三方 API 的 import 吗？
  │     ├─ 不会 ──────────────────────────────► src/（(a) 类，永远不许加 MC import）
  │     └─ 会 → Q2
  │
  ├─ Q2 它是业务编排吗？（*VisualController / *Manager / *UI / 命令流程 / 数据模型）
  │     ├─ 是 ────────────────────────────────► src/（(b) 类，靠调用接口消化版本差异，禁止搬 versions/）
  │     └─ 否 → Q3
  │
  ├─ Q3 各版本的实现差异 ≤3 行、且只在一个方法内吗？
  │     ├─ 是 ────────────────────────────────► src/ 原文件 + //? if 条件注释（规则 3）
  │     └─ 否 → Q4
  │
  ├─ Q4 接口放 src/（零 MC import），实现放 versions/，类名带版本后缀（规则 2）
  │
  └─ Q5 共享侧怎么拿到实现？接法 1 优先：versions/<v>/ 各放一个同名工厂类（规则 5）
```

**再补两条硬检查（每次提交前跑）**
1. `versions/<v>/` 里的每个类名，在 `src/` 里 grep 一遍必须为 0 命中（否则 `错误: 类重复`）。

### 5.3 交接点（规则 5 接法 1：每个版本目录各放一个**同名**工厂类）

```java
// versions/1.20.4/src/main/java/areahint/network/IdentifiersFactory.java
```

### 5.4 编译时各节点分别看得见哪个实现（关键）

| 节点 | 参与编译的版本目录 | 该节点可见的实现类 | 共享 `src/` |
|---|---|---|---|
| `:1.20.4` | `versions/1.20.4/src/{main,client}/java` | `Identifiers1204` + `IdentifiersFactory` | 全部参与编译 |
| `:1.21.1`（骨架） | `versions/1.21.1/skeleton/{main,client}/java` | `Identifiers1211` + `IdentifiersFactory` | **不参与编译**（`setSrcDirs` 整体替换） |
| `:1.20.1`（将来，非骨架） | `versions/1.20.1/src/{main,client}/java` | `Identifiers1201` + `IdentifiersFactory` | 全部参与编译 |

**为什么不会冲突**：任意两个同名类（两份 `IdentifiersFactory`、`Identifiers1204` 与 `Identifiers1211`）**不会进入同一次 javac**——每个节点只挂载自己那一个版本目录（阶段 0 探针 A/B 实测）。

已落地的 `NetworkCompat` 家族同理：`:1.20.4` 只看得见 `versions/1.20.4/` 下的 `NetworkCompatFactory`，`:1.21.1` 将来只看得见它自己那份同名工厂——两份同名工厂永远不会进同一次 javac。
